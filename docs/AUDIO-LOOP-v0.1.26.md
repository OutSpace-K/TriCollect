# v0.1.26 音乐素材循环接缝候选修复

## 已证实的问题与本次范围

基线为 `e3c9ad4` / v0.1.25。原始 `assets/ambience.wav` 是32秒、22050Hz、单声道16位PCM，精确对应135BPM的18小节。末尾980个采样全为零，共44.44ms。旧验证只检查首尾采样差和播放器会回到开头，这两项不能发现一段静音，也不能证明微信播放无停顿。

曲内另有类似长度的休止。因此，尾部全静音是可测的素材问题，**还不能认定它就是用户所听间断的唯一原因**。微信原生播放器在重新开始一轮时是否另有解码/调度延迟，本次没有真机测量。

本次只延长最后一个旋律音的余音，使用生成器已有的环形写入把余音接到下一轮开头。不裁掉尾部、不改变节拍或总时长、不提高默认音量、不扩成长文件。其他旋律与取球音效保持。`scripts/make-audio.py` 可重制素材；重复生成的WAV字节一致。

微信仍使用单个原生 `InnerAudioContext`，保留 `loop = true`、全局与实例的 `obeyMuteSwitch = false`，并保持首次触摸重试、游戏静音、暂停、广告、后台与系统音频中断逻辑。没有使用双播放器或JavaScript定时器接力。

没有贸然切换到WebAudio：项目锁定的微信官方类型声明明确提示 `setInnerAudioOption` 不兼容 `createWebAudioContext` 及启用 `useWebAudioImplement` 的播放器。当前没有设备证据可证明切换后仍保留上版声音兼容性。

## 信号分析

- 总时长仍为32秒，705600帧，文件大小仍为1411244字节。
- 尾部全静音：44.44ms → 0ms。
- 接缝附近每个10ms窗的最低RMS：0 → 0.01219。
- 峰值保持约0.334，没有削波，整体RMS基本不变。
- 首尾采样差约0.00861，接缝相邻斜率变化约0.00101/0.00330。这是余音连续波形的一部分，不以“首尾都为零”冒充无缝。
- 详细量化结果见 `evidence/v0.1.26-audio-signal.json`，合成层级结果见 `evidence/v0.1.26-audio-synthesis.json`。

## 自动验证与限制

- 新增素材回归检查PCM格式、精确小节时长、削波、接缝短窗能量、相邻波形变化及两端预构建音频与源码素材一致。
- 该接缝检查在旧素材上实际失败，说明能捕获原来的尾部静音；旧版失败记录是刻意执行的回归对照，不是最终候选测试失败。
- 新增检查确保音乐仍使用支持原静音键配置的原生后端。
- 最终源码全量133项测试通过；两端构建、类型检查、Prettier和diff空白检查通过。额外验证三档共300个种子，见证路线均无广告获胜且球身份守恒。
- 测试使用 `node --import tsx --test --test-concurrency=1 tests/*.test.ts`，种子使用 `node --import tsx scripts/verify-seeds.ts`；这是相同tsx测试引擎的Node入口。原生命令入口与浏览器验证不可混为一谈。结果见本版本 `evidence` 文件。
- 浏览器音频测试尝试启动Chromium时，被宿主Unix socket权限限制阻断，未执行到网页播放。不能把单元测试或PCM分析当作浏览器解码/听测通过。
- **没有人工听测，没有运行微信开发者工具或iOS/Android体验版；本次不能宣布用户设备的循环间断已经完全解决。**
